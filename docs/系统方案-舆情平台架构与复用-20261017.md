# 系统方案 · 舆情监测平台「对齐目标平台 + 复用现有资产」

- 日期：2026-10-17
- 适用对象：`sentiment-monitor`（v0.05，HEAD `a035e7d`）+ `agent-bridge`（协议桥）+ 本机 DSH
- 参考对象：B 站那套多 Agent 舆情平台（LangGraph + LangChain + Elasticsearch），页面为 总览大屏 / 话题分析 / 舆情检索 / 预警中心 / 报告管理 / 系统设置，Agent 为 SCHEDULER / CRAWLER / CLEANER / SENTIMENT / CLUSTER / TOPIC / ALERT

---

## 1. 结论先行

1. **不要重写**。现有 `sentiment-monitor` 已经把最难的部分做了：真实采集（8 源 / 19 批 / 148 条）、去重（133 条 canonical）、时间质量标注、P1 证据与观察期、只读任务视图。
   目标平台剩下的四块——**总览聚合、话题聚类可视化、预警调度、报告归档**——都是"在已有表上加一层"的活，不需要引入 LangGraph/ES。
2. **多 Agent 编排直接用协议桥**，不必自建调度框架：桥已经有「契约 → 计划 → 独立 worktree 执行 → 证据回传 → 评审门」的完整闭环，`taskboard.py` 已经是它的只读大屏。目标平台里的 CRAWLER/CLEANER/SENTIMENT/CLUSTER 都可以作为桥任务下发，产物落回 `sentiment.db`。
3. **先补 3 个硬缺口**（都有实测证据）：`/api/overview-stats` 不存在（404 实测）、`analysis` 的 `adapter not_configured` + `production_status BLOCKED`、148 条里 138 条没有发布时间（93.2%）。

## 3. 可复用的开源项目（按"能省多少活"排序）

| 项目 | 可复用部分 | 怎么用 | 风险 |
|---|---|---|---|
| [BettaFish (666ghj)](https://github.com/666ghj/BettaFish) | 多 Agent 舆情分析流程、情感/主题提示词、报告模板 | 抽取其 prompt 与报告结构，作为 `analysis.py` 的生产适配器；不整体引入 | 体量大，需裁 |
| [TrendRadar (SANSAN0)](https://github.com/SANSAN0/TrendRadar) | 热榜采集源清单、去重规则、日报模板 | 补充 `feeds`（热榜类），复用其去重/排序启发式 | Python 依赖需本地化 |
| [twitter_trend_agent](https://github.com/peige-guo/twitter_trend_agent) | 趋势聚合与话题抽取思路 | 话题抽取规则参考 | 数据源不可达（境内） |
| MediaCrawler / OpenCLI | 小红书/抖音/B站采集 | 仅作"可选源"，按需接入 | 账号风控，谨慎 |
| DSH `dsh-verify`（本机已装） | 真实浏览器验收 | 每个新增页面都用它出 PASS/FAIL 证据 | 无 |

原则：**只抄流程与提示词，不抄运行时**。现有 SQLite 单文件 + 两个 stdlib HTTP 服务的形态已经够用（148 条量级），引入 ES/Redis 是负收益。

## 4. 分阶段实施（P1 → P3）

### P1：把"有数据但没页面"的部分做完（1–2 天）

| 任务 | 交付 | 验收 |
|---|---|---|
| 总览聚合接口 | `GET /api/overview-stats?window=7d` → KPI（今日/本周条数、来源数、去重率、时间有效率）、趋势序列、情感分布、平台分布、话题 TOP10 | 返回 JSON；`app.js` 4 张图渲染；数值与 `records` 直查一致 |
| 话题分析页接线 | 读 `analysis_jobs` + 事件文件（`events/*.jsonl`），出话题列表与详情 | 页面能看到真实分组，不再是占位 |
| 情感/聚类接生产 | `analysis.py` 的 adapter 从 `not_configured` 变为可用（先用规则 + 可选模型增强） | `production_status` 不再是 `BLOCKED` |
| Agent 日志面板 | `GET /api/agent-log/stream`（SSE）或 2s 轮询 tail 桥的 `events.jsonl` | 页面上能看到桥任务实时步进 |
| 时间质量修复 | 采集侧补发布时间解析（现在 93.2% 缺失），或在 UI 明确标注"发布时间未知" | `unknown_time_ratio` 明显下降或有明确降级说明 |

### P2：预警中心 + 报告管理（2–4 天）

- 新表：`alert_rules`（关键词/来源/阈值/窗口/级别/冷却）、`alerts`（命中的规则、证据 id、首次/末次时间、状态）、`notifications`（通道、结果）。
- 调度：先做最简版本——`server.py` 内的 60s 定时线程按 `alert_rules` 扫 `records`/`canonical_records`，命中写 `alerts`；通知先落库 + 页面展示，SMTP 留接口。
- 报告：`reports` 表 + `GET /api/reports`、`POST /api/reports/generate`（模板 → Markdown/HTML → 归档到 `reports/<date>/`）。
- 验收：造一条会命中的样本，确认 60s 内出现告警；生成一份报告并能下载。

### P3：系统设置 + 采集调度（3–5 天）

- `settings` 表（限流、并发、端口、路径、保留期）；页面可改并有哈希校验。
- 采集调度：`schedules` 表 + 定时触发 `collection_runs`；与桥的 SCHEDULER 角色对应。

## 5. 数据模型增量（建议 DDL 摘要）

```sql
CREATE TABLE IF NOT EXISTS alert_rules (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, enabled INTEGER DEFAULT 1,
  match_kind TEXT NOT NULL,        -- keyword | source | sentiment | topic
  match_value TEXT NOT NULL,       -- JSON
  window_minutes INTEGER DEFAULT 60, threshold INTEGER DEFAULT 1,
  level TEXT DEFAULT 'info',       -- info | warn | critical
  cooldown_minutes INTEGER DEFAULT 30, created_at TEXT NOT NULL);

CREATE TABLE IF NOT EXISTS alerts (
  id INTEGER PRIMARY KEY, rule_id INTEGER NOT NULL,
  level TEXT NOT NULL, metrics TEXT, evidence TEXT,   -- JSON
  first_seen TEXT NOT NULL, last_seen TEXT NOT NULL,
  status TEXT DEFAULT 'open',          -- open | acked | closed
  UNIQUE(rule_id, first_seen));

CREATE TABLE IF NOT EXISTS reports (
  id INTEGER PRIMARY KEY, kind TEXT NOT NULL, period_start TEXT, period_end TEXT,
  path TEXT NOT NULL, sha256 TEXT NOT NULL, created_at TEXT NOT NULL);

CREATE TABLE IF NOT EXISTS schedules (
  id INTEGER PRIMARY KEY, kind TEXT NOT NULL, cron TEXT NOT NULL,
  enabled INTEGER DEFAULT 1, last_run_at TEXT, last_status TEXT);
```

另有两条**必须补的索引**（现在按来源/时间查都靠全表扫）：
```sql
CREATE INDEX IF NOT EXISTS idx_records_feed_pub ON records(feed_id, published_at);
CREATE INDEX IF NOT EXISTS idx_canonical_created ON canonical_records(created_at);
```

## 7. 多 Agent 编排（用桥，不引 LangGraph）

```
SCHEDULER  ──submit──▶ 协议桥 ──plan/run──▶ worktree 内执行（opencode 或 dsh）
    ▲                     │                        │
    │                     │◀──── 证据回传（before/after/changes.diff/result.json）
    │                     ▼
 定时/事件          评审门（reviewable / review_gate）
                          │
                          ▼
              sentiment.db（canonical_records / analysis_jobs / alerts / reports）
                          │
                          ▼
                     taskboard.py（只读大屏）+ 观察台页面
```

落地要点：
- 每个 Agent 一个契约模板（`templates/contract-*.json` 已有先例：docs-only / modify-adapter / add-endpoint / add-annotator）。
- **执行通道已修好**：提示词走 stdin（不再有 32,767 字符限制），`opencode_mode=service` 复用后台服务（省约 1.2s/任务）；真实 39KB 契约已跑通（R0 审查，exit 0、`reviewable=true`）。
- 成本：`native_cost` 目前恒为 `null`，P1 必须补上，否则多 Agent 跑起来没有账。

## 8. 风险与依赖

| 风险 | 影响 | 对策 |
|---|---|---|
| 发布时间缺失 93.2% | 趋势图不可信 | P1 修采集解析；UI 明确标注未知 |
| `coverage=sample_only` | 结论不能外推 | 页面显著位置标注数据覆盖口径 |
| opencode 后台服务不自启 | 桥静默回落，慢 1.2s/任务 | 已改为显式警告；建议加开机自启 |
| 桥 22+ 任务停在 `awaiting_review` | 大屏噪音、真问题被淹 | 逐个收口或明确放弃 |
| 预警通知需要 SMTP | P2 可能卡住 | 先落库+页面，SMTP 后置 |
| 采集源风控 | 采集中断 | 保留 `collection_runs.error` 可视化 |

## 10. 验收口径（沿用现有项目纪律）

1. 每个页面必须有 **真实浏览器** 证据（`dsh-verify` 或截图 + 关键数值），不接受"进程没崩"。
2. 每个接口必须给出 **与 SQL 直查一致** 的数字对拍。
3. 数字类结论必须标注口径（窗口、样本量、覆盖率）。
4. 桥侧任务一律走契约 + 评审门，产物路径必须落在 `allowed_paths` 内。
