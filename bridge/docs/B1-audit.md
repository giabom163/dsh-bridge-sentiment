## 具体缺陷及最小修复

### F1 — 首次列表请求失败被显示成“暂无任务”

- **定位：** `web/app.js:2,46-50,53-59`；`web/task-graph.js:163-169,201-204,226-237`；`web/index.html:31-33`。
- **表现：** `state.tasks` 初始为空。若首次 `GET /api/tasks` 失败，catch 调用 `renderGraph()`；该函数仍调用 `graph.update([])`，而列表/空态分别只按任务数组是否为空显示“暂无任务”。在图组件成功挂载的情况下，此时没有成功读取任务，数据实际是未知，不足以断言任务为空。页面同时显示断连，并不能消除空态误导。
- **最小修复：** 区分“尚未成功加载”和“成功加载且确为空”（例如增加 `hasLoadedTasks`）；仅在成功列表响应后显示空图/暂无任务。首次失败显示“无法读取任务/等待重试”，成功后的后续断线则继续保留旧数据和旧时间。表格空态也应遵循同一判别。
- **验证要求：** 由主线程在浏览器中分别观察首次 GET 失败、成功空列表、已有数据后断线三种情况；静态断言不能代替观察。

### F2 — `--limit` 不限制实际执行的检查组

- **定位：** `tests/graph_checks.py:185-200`。
- **表现：** 第 188-190 行无条件运行三组检查，到第 199 行才执行 `checks[:args.limit]`。因此 `--limit 1` 或 `--limit 2` 仍会运行三组，只是少打印/记录结果；这不符合脚本宣称的限量语义。当前说明记录的是 `--limit 3`，所以这一点不否定其所记三组执行，但脚本对其他合法限值并未真正限量。
- **最小修复：** 按 `args.limit` 控制检查执行循环，只执行前 N 组；不要在执行全部检查后再切片。修改后仍按项目约束由执行者首次使用 `--limit 3`，本复审不运行。

### F3 — “loaded_hashes_match” 机器记录没有比对全部实际响应字节

- **定位：** `tests/graph_checks.py:128-157`，尤其 `139-143`；`webui.py:41-43,147-152`。
- **表现：** 检查将 runtime 的图 JS 哈希与本地磁盘文件比较；Cytoscape 还比对 HTTP 响应体。但没有将图 JS 的 HTTP 响应体做哈希比较，也没有获取并校验 `/app.js`、`/index.html`、`/style.css` 响应体对应的 runtime 哈希。因此输出字段 `loaded_hashes_match: true` 不能单独证明所有实际服务的 UI 字节均匹配 runtime 记录。服务路由的逐项路径及当前哈希构造可静态核对，但机器记录的断言比字段名所表达的范围窄。
- **最小修复：** 若保留该字段，定向检查应对每个实际加载资源比较 runtime 哈希与 HTTP 响应体 SHA-256；或把输出字段/说明收窄为实际已验证的资源范围。
